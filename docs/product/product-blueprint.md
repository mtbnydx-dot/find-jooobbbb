# 求职产品蓝图

> 文档状态：产品化开发基线
> 适用分支：`feature/job-platform-productization`
> 目标：在保留现有岗位采集与去重能力的前提下，把单人岗位看板扩展为可服务多专业、多地区、多薪资偏好的多用户求职产品。

## 1. 当前代码事实

现有系统已经具备可复用的“内容运营底座”：

- `server/cloud/adapters.js` 负责飞书、腾讯文档、HTML、JSON、Excel 等来源采集。
- `server/cloud/classifier.js` 负责岗位清洗、规则分类和跨来源 canonical 去重。
- `server/cloud/runtime.js` 负责任务队列、定时同步、提醒、面经搜索和 DeepSeek 批量评估。
- `server/server.js` 提供岗位、状态、信息源、运行记录和 AI 接口。
- `server/public/` 是响应式单页管理看板，已经能在桌面和手机浏览器使用。

原系统是单人工作台；当前产品化分支已完成第一版隔离：

- `jobs.json` 继续保存旧运营状态；用户端私有状态改存 `product.db`，按 `user_id + job_id` 隔离。
- `cloud.db` 的旧 DeepSeek 配置仍是平台运营级能力，旧全局评估不会返回为新用户的个人匹配结果。
- 默认 AI 画像写死为传播学背景；规则筛选写死为 2027 届秋招、固定城市和一组传播/营销方向。
- 采集链现已保留专业、学历、经验、描述、要求、技能、工作方式、用工类型、薪资、币种、周期、发薪月数和福利字段；来源未提供时保持未知。
- “笔经面经”搜索仍只是运营资料；另有 8 条路径、24 道原创题和独立用户答题进度，但尚无版本化内容工作流。
- 已有用户、会话、角色、套餐、权益和用量实体；真实账单、退款和支付 webhook 尚未接通。

当前产品化分支已经把上述模块接入 `product.db`、`/api/v1`、`/app/` 和自动化回归测试。它可以作为本机演示和后续灰度的底座，但真实支付、通知、原生商店包、内容授权和商业薪资数据仍需单独验收。

因此产品化不能简单地在当前页面上增加一个登录框。正确边界是把采集系统保留为平台运营面，再增加独立的用户产品面。

## 2. 产品边界

```text
平台内容运营面
信息源登录 / 采集 / 去重 / 字段清洗 / 岗位审核 / 题库发布 / AI 成本
                              |
                     全局岗位与内容目录
                              |
用户产品面
账号 / 职业画像 / 个性推荐 / 投递进度 / 薪资偏好 / 备考 / 套餐权益
```

### 2.1 全局共享内容

- 岗位基础事实、来源、更新时间和失效状态。
- 公司、行业、岗位族、专业、学历、地区等分类体系。
- 经审核发布的题目、解析、学习路径和通用面经链接。
- 套餐定义和公开价格目录。

### 2.2 用户私有内容

- 账号、职业画像、简历资料和目标岗位。
- 收藏、隐藏、投递阶段、下一步、联系人和备注。
- 针对具体画像生成的 AI 推荐结果。
- 薪资底线、目标待遇、真实 Offer 和对比记录。
- 答题、错题、学习计划和辅导记录。
- 订阅、权益、用量、退款和服务额度。

### 2.3 普通用户不可见的能力

- 飞书、腾讯文档等信息源配置和服务器浏览器登录会话。
- DeepSeek API Key、全局模型参数、采集队列和运行错误详情。
- 全体用户列表、人工授权、题库发布和内容版权信息。
- 支付 webhook、内部成本和平台审计记录。

## 3. 角色与授权

| 角色 | 主要能力 | 明确限制 |
|---|---|---|
| `user` | 管理自己的画像、岗位状态、薪资偏好、备考和订阅 | 不得读取其他用户数据或运营配置 |
| `content_editor` | 维护岗位分类、题目、解析和学习路径 | 不得管理支付密钥或用户角色 |
| `admin` | 管理来源、模型、用户角色、人工套餐、内容和运行状态 | 当前仍需补完整的敏感操作审计记录 |

`coach`、`support` 与授权委托模型属于后续阶段；在服务端存在对应资源范围前，不应只增加角色名称。

授权必须在服务端判断。隐藏前端按钮不等于授权。

## 4. 信息架构

### 4.1 用户端

桌面端主导航：

1. 首页：今日推荐、即将截止、待办、学习计划和本周进度。
2. 找岗位：搜索、推荐、专业/学历/地点/薪资等筛选和岗位详情。
3. 求职进度：收藏、计划投递、已投递、笔试、面试、Offer 和失利复盘。
4. 备考：岗位族学习路径、诊断、题库、错题和学习计划。
5. 薪资与 Offer：期望设置、岗位待遇、Offer 对比和谈薪准备。
6. 我的：职业画像、账号、通知、用量、套餐和数据导出。

手机端使用底部主导航：`首页 / 岗位 / 进度 / 备考 / 我的`。薪资、套餐、通知和设置放入“我的”，不复制一套独立移动业务逻辑。

### 4.2 管理员端

管理员端当前分为 `/app/admin/users`（用户角色与套餐）和 `/ops`（来源、运行、AI 等旧运营面）。后续可收敛为统一管理端：

1. 内容总览：岗位质量、来源新鲜度、待审核内容和异常。
2. 信息源：采集链接、授权会话、字段映射、运行和去重。
3. 岗位运营：分类、薪资修正、失效、合并和用户纠错。
4. 题库运营：草稿、复核、发布、下架、版权和版本。
5. 用户与权限：账号状态、角色、人工套餐授权和数据请求。
6. 套餐与订单：价格、权益、订阅状态、退款和服务额度。
7. AI 与成本：模型、提示词版本、用量、缓存命中和失败记录。

## 5. 职业画像与多专业支持

当前一个用户拥有一份可包含多个专业、岗位、行业、技能和地点的画像；未来若验证出明显需求，再扩展为多个独立 `career_profiles`。建议字段如下：

### 5.1 教育与经历

- `career_stage`：学生、应届、在职、转行、自由职业。
- `graduation_year`、`highest_degree_id`。
- `major_ids`、`minor_major_ids`，必须引用分类 ID，允许跨学科多选。
- 学校、课程、证书、语言及熟练度。
- 实习、项目、作品集和工作年限摘要。
- `available_from`、工作授权和签证状态。

### 5.2 求职目标

- `target_role_ids`、`target_job_family_ids`、`target_industry_ids`。
- `preferred_location_ids`、是否接受异地、远程和搬迁。
- 全职、实习、合同、兼职等就业类型。
- 公司规模、企业性质、稳定性和成长偏好。
- 必须满足项、明确排除项和可协商项。

### 5.3 能力证据

- `skill_ids` 与熟练度、使用年限、证据摘要。
- 项目、实习和作品集与目标岗位的关联。
- 不能仅依据专业名称判断胜任度；专业是一个维度，技能和可证明经历是更强证据。

### 5.4 画像版本

每次影响推荐的修改都增加 `profile_version`。AI 缓存键至少包括：

```text
user_id + profile_id + profile_version + job_id + job_content_hash + model_version
```

这样一个用户修改画像只会使自己的结果过期，不会覆盖其他人的推荐。

## 6. 薪资和待遇

岗位待遇、用户期望和真实 Offer 是三个不同对象，不能混用。

### 6.1 岗位待遇

- `raw_salary`：保留来源原文，例如 `15-25K·14薪`、`面议`。
- `salary_min`、`salary_max`、`currency`。
- `pay_period`：小时、天、月、年。
- `pay_months`：中国岗位常见的 13、14、16 薪。
- `bonus_text`、`equity_text`、`benefits`。
- `normalized_annual_min/max`、计算规则和汇率日期。
- `source_confidence`、`verified_at`。

### 6.2 用户期望

- 最低和目标基本薪资、总包目标、币种和周期。
- 奖金、股权、远程、签证、住房、搬迁等福利优先级。
- 是否接受薪资未知或面议岗位。

### 6.3 Offer 记录

- 公司、岗位、基本薪资、奖金、股权、福利、币种和有效期。
- 是否接受、谈判轮次、私人备注和对比结论。
- Offer 数据默认只对本人可见。

### 6.4 展示与比较规则

- 未知值必须显示“未披露”，不能按 0 参与排序。
- 跨币种比较必须展示汇率来源和日期，允许用户关闭换算。
- 年化计算必须同时展示原始薪资表达，避免隐藏发薪月数和奖金不确定性。
- AI 不得编造岗位待遇；推测只能标为“估算”，不能进入已验证字段。

## 7. 个性推荐

推荐链路分为四层：

1. 数据质量：确认岗位有效、来源新鲜、字段可用。
2. 资格检查：毕业届、学历、专业限制、经验、工作授权等明确条件。
3. 确定性匹配：岗位族、技能、地点、薪资、行业和就业类型。
4. AI 解释与排序：结合用户经历给出理由、缺口和准备建议。

推荐结果建议包含：

- `score` 与推荐等级。
- `dimension_scores`：资格、方向、技能、专业学历、地点、薪资、行业。
- `hard_checks`：通过、失败、未知。
- `positives`：来自用户画像和岗位原文的正向证据。
- `gaps`：真实缺口及可执行的补强建议。
- `unknowns`：岗位没有披露、不能可靠判断的条件。
- `reason`、`confidence`、画像版本、岗位版本和生成时间。

推荐页面必须允许用户查看“为什么推荐”和“为什么不推荐”，并能调整偏好权重。未知薪资不能直接导致低分，明确不满足硬条件时则必须醒目提示。

## 8. 求职进度

建议用以下用户状态替代当前过于简化的全局状态：

```text
discovered -> saved -> planned -> applied
                         |          |
                         |          +-> online_assessment
                         |          +-> interview_1 -> interview_2 -> final
                         |          +-> offer
                         |          +-> rejected / withdrawn
                         +-> archived
```

`user_job_states` 至少包含：

- `user_id + job_id` 唯一键。
- 收藏、隐藏、阶段、自定义标签和排序。
- `applied_at`、`stage_changed_at`、`next_action_at`。
- 私人备注、联系人和结果复盘。

进入笔试或面试阶段后，可自动推荐对应岗位族的备考路径；Offer 阶段则进入薪资与谈判模块。

## 9. 备考建议与题库

### 9.1 内容实体

- `prep_tracks`：适用岗位族、阶段和预计时长。
- `prep_modules`：学习顺序和知识点。
- `prep_questions`：题型、难度、题干、选项、答案、解析和评分量表。
- `question_versions`：内容版本、作者、复核人和变更说明。
- `question_attempts`：用户答案、得分、耗时和反馈。
- `study_plans`：目标岗位、考试日期、每日任务和完成状态。
- `prep_progress`：掌握度、薄弱点、错题和建议复习时间。

### 9.2 题型

- 单选、多选、数值、排序。
- 简答、行为面试、案例分析、作品集陈述。
- 主观题必须区分规则量表、AI 反馈和真人教练反馈，不能把三者混称为专业人工评分。

### 9.3 最小种子内容

`server/product/catalog.js` 当前种子已经提供 8 条学习路径、每条 3 道原创题，共 24 道：

1. 求职基础与简历。
2. 行为面试与 STAR。
3. 软件与互联网研发。
4. 数据与商业分析。
5. 产品与运营。
6. 市场、品牌与传媒。
7. 财务、金融与咨询。
8. 工程制造与供应链。

现有种子已经包含题型、难度、题干、答案和解析；接入持久化内容系统时还必须补充技能标签、预计耗时、来源类型、版权状态、发布状态和版本。销售、客户成功、人力、法务、医疗、教育、设计和作品集等仍是后续应补齐的专业覆盖。企业真题只有在拥有合法授权时才能进入收费题库。

## 10. 套餐与权益

核心岗位浏览、申请链接和基本投递管理应保持免费。收费应围绕个性化效率、深度备考和真人服务。

`server/product/catalog.js` 当前保存的第一版产品假设如下：

| 能力 | Free | Pro | Coach |
|---|---:|---:|---:|
| 专业标签上限 `profile.majors` | 3 | 10 | 20 |
| 可用备考路径 `prep.tracks` | 2 | 不限 | 不限 |
| 答题 `prep.attempts.daily` | 5/日 | 100/日 | 500/日 |
| 薪资洞察 `salary.insights` | 否 | 是 | 是 |
| 辅导反馈 `coach.feedback` | 0 | 0 | 0（服务上线前不销售） |
| 静态月价假设 | ¥0 | ¥39 | ¥129 |

这些套餐与额度已经写入 `product.db`，并由服务端执行专业数量、题库路径、每日答题和薪酬洞察限制；管理员可以人工授权。它们仍只是定价假设，不代表真实订阅或支付已经接通。价格、周期和地区币种后续应配置化并可版本化；Coach 在真实教练、交付物、时限和退款规则齐备前保持不可购买。

## 11. 建议 API 边界

用户端：

- `POST /api/v1/auth/register|login|logout`
- `GET /api/v1/me`
- `GET|POST|PATCH /api/v1/me/profiles`
- `GET /api/v1/taxonomies`
- `GET /api/v1/jobs`、`GET /api/v1/jobs/:id`
- `GET /api/v1/recommendations`、`POST /api/v1/recommendations/refresh`
- `PUT /api/v1/me/jobs/:id/state`
- `GET /api/v1/me/pipeline`、`GET /api/v1/me/dashboard`
- `GET /api/v1/prep/tracks`、`POST /api/v1/prep/attempts`
- `GET /api/v1/prep/progress`、`POST /api/v1/prep/study-plans`
- `GET /api/v1/plans`、`GET /api/v1/me/subscription|usage`

管理员端：

- `/api/v1/admin/sources|runs|jobs`
- `/api/v1/admin/taxonomies`
- `/api/v1/admin/prep/*`
- `/api/v1/admin/users|roles|entitlements`
- `/api/v1/admin/plans|orders`
- `/api/v1/admin/ai/*`

旧 `/api/cloud/*` 可在迁移期保留给管理员，但不能继续作为普通用户接口。

## 12. 迁移原则

- 全局岗位内容继续保留，避免重复导入和破坏现有 canonical ID。
- 创建明确的旧数据所属账户，把现有状态、备注和自选岗位迁移到该账户的 `user_job_states`。
- 信息源、浏览器授权和 DeepSeek Key 继续作为平台级运营配置。
- 现有 AI 结果可保留为历史记录，但不能冒充新用户的个性推荐；用户完成画像后应按新缓存键评估。
- 迁移前后校验岗位数、状态数、备注数、自选岗位数和 AI 结果数，提供可回滚备份。

## 13. 阶段验收

### 阶段一：产品底座与可演示闭环

- 可以注册、登录、退出并读取当前用户。
- 两个用户共享岗位目录，但画像、岗位状态、备注、推荐、答题和权益完全隔离。
- 至少支持多专业、多学历、多岗位族、多地区和薪资偏好。
- 同一批岗位对传播、计算机、财务等不同画像产生不同推荐及解释。
- Free、Pro、Coach 套餐目录可展示，服务端可执行人工授权和用量限制。
- 至少 24 道已发布原创题可以练习、评分、查看解析和累计个人进度。
- 普通用户无法访问来源、全局 AI Key、运行中心和管理员接口。
- 桌面和主流手机浏览器完成登录、画像、找岗位、改进度、答题和查看套餐闭环。
- 未接真实支付时，升级动作必须明确显示“支付尚未开放”或进入申请试用，不能返回伪造支付成功。

### 阶段二：真实商业闭环

- 接通至少一个真实支付渠道，并以服务端 webhook 幂等地授予、续期和回收权益。
- 邮件、站内通知和必要的退订流程可验证送达。
- 题库有草稿、复核、发布、下架和版本审计。
- 薪资字段具有来源、更新时间和纠错流程。
- 能统计激活、推荐点击、收藏、投递、面试、备考完成、付费转化和流失，但不把相关性夸大为因果。

### 阶段三：规模与原生交付

- 数据库、后台任务和缓存可支持多实例，采集浏览器与用户 API 解耦。
- 完成 Android/iOS 包装、签名、推送、商店合规和真机兼容验证。
- Coach 具有真实教练、预约、交付、评价、退款和服务等级流程。

## 14. Android、iOS、Web 与 PWA 边界

第一阶段推荐“一套响应式 Web + PWA”：

- Web 使用语义化 HTML、响应式布局、触控尺寸、安全区和键盘可达性。
- PWA 提供 manifest、图标、service worker、可安装入口和有限离线壳。
- iOS Safari 和 Android Chrome 均需真机验证登录、表单、滚动、文件选择和安装体验。
- 所有核心业务规则位于服务端，避免 Web、Android、iOS 出现三套不一致逻辑。

必须明确：

- “手机浏览器适配”不等于 PWA 已可安装。
- “PWA 可安装”不等于 Apple App Store 或 Google Play 原生应用已经发布。
- Capacitor 等包装配置不等于已完成签名、真机测试、推送证书、隐私清单、应用内购买和商店审核。
- 离线壳不等于岗位、推荐和投递数据支持完整离线编辑；若未实现冲突合并，应保持只读缓存。

## 15. 第一阶段非目标

- 不在没有商户资质和 webhook 的情况下模拟真实扣款。
- 不在没有内容授权的情况下批量搬运企业真题。
- 不用 AI 猜测值填充“已验证薪资”。
- 不把响应式网页宣传为已上架的原生应用。
- 不在没有教练供给、排期和退款流程时销售 Coach 服务。
- 不承诺 AI 推荐必然获得面试或 Offer。
